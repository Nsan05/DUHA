09/01/2026:
- Explored affine objects tells you how to convert pixel coordinates into real world coordinates those 6 numbers are:
Scale X: How wide is one pixel? (e.g., 30 meters)

Shear X: Is the map tilted? (Usually 0)

Origin X: Where does the map start (West edge)?

Shear Y: Is the map tilted? (Usually 0)

Scale Y: How tall is one pixel? (Usually -30 meters, because maps go "down" from North).

Origin Y: Where does the map start (North edge)?
- Created the urban mask tif file that follows the mater grid style raster from the geojson file.
- Moved on to sentinel data processing.
- Manual data processing too slow.
- Optimisation done:

1. The "Windowed" Approach (RAM Optimization)
Problem: You have 15 massive satellite images. Loading them all into RAM requires >30GB. Your computer would crash.
Solution: We cut the city into small 2km squares (Windows).
Action: The script loads only the data for one square, processes it, saves it, clears RAM, and moves to the next square. It never holds more than ~100MB in memory at once.

2. Granule Filtering (Speed Optimization 1)
Problem: Sentinel-2 splits the world into tiles (Granules). For any given 2km square in Dubai, maybe only 1 or 2 Granules actually cover it. The others are miles away.
Naïve way: Try to read from all 15 files every time (Slow!).
Our way: We defined a "Bounding Box" for every Granule. Before processing a square, we ask: "Which granules actually touch this square?" If the answer is "None", we skip it instantly.

3. Urban Mask Check (Speed Optimization 2)
Problem: A huge chunk of the map is just empty desert or sea (Background).
Optimization: Before doing any heavy math, we check your urban_mask_30m.tif.
Logic: "Is this square entirely '0' (Background)?"
Yes: Skip it immediately.
No: Process it.
Result: We skipped ~60% of the work (all the desert blocks), finishing in minutes instead of hours.

- Looked into ways to implement OSM rasterization. 
- The Problem: The target map is 30m resolution. A typical road is only 10m wide. If you rasterize normally, a 30m pixel containing a road might just be labeled "1" (Road). This suggests the entire 30m x 30m area is paved, which is false. It exaggerates the urban heat effect.

The Solution: Create a temporary grid that is 10x higher resolution (3m). We draw the road there, then "squash" (average) it back down to 30m. This gives us a fractional value (e.g., 0.33) representing accurate coverage.
